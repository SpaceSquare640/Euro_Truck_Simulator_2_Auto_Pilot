# Desktop UI preview

This is the .NET 10 WPF shell for the external ETS2 Auto Pilot app. It provides Overview, Setup, Settings, and Activity screens; Windows theme following with light, dark, and high contrast palettes; keyboard navigation (Ctrl+1 through Ctrl+4); and local theme and game-folder preferences. The Overview also shows v1.1 frame, focus, physical-input, lane-confidence, and obstacle-check observations so unavailable safety evidence is visible.

All displayed text is loaded from the English `Resources/Strings.resx` resource. With a verified Python UI status service, the Overview separates the pipe connection from live game telemetry and, with UI IPC v1.1, displays current perception and input-monitor observations. The checklist marks the game and connector available only when telemetry is fresh; the control service remains unavailable, and auto pilot engagement stays disabled because the control path and required safety gates are incomplete. ETA is explicitly marked as unavailable because the UI protocol does not carry navigation time. The Activity page records connection, telemetry, service-state, and error transitions in memory for the current session only; Copy status copies a compact diagnostic snapshot without local paths. During connector installation, the Setup page shows an indeterminate progress indicator. Select the game folder and choose Install connector. The elevated installer downloads the matching `ETS2AP_DLL_V<version>.zip` asset from a published GitHub Release, verifies the release SHA-256 digest and ZIP manifest in memory, then copies the supported plugin DLLs into `bin/win_x64/plugins`. Existing same-name DLLs are backed up in a sibling `ETS2AP_Backups_*` folder. During installation it holds no-delete handles on the selected local directory chain and rejects junctions or other reparse points. The installer does not edit ETS2 control bindings; automatic binding and native control remain unfinished.

The installed app starts the bundled Python status service automatically from `runtime\python.exe`; users do not select a Python installation or provide a command-line path. The service runs hidden, is terminated when the WPF app closes, and receives one automatic restart after an unexpected exit. A missing runtime or service package leaves the UI offline. The service remains status-only and does not enable engagement. For development pipe checks, see the [Python service instructions](../python/README.md).

The WPF process publishes the `perception.v1` mapping at approximately 20 Hz. It prefers a fresh read-only `gameframe.v1` D3D11 image from the native plugin, then falls back to downsampling a GDI desktop capture of the ETS2 client rectangle to 160 × 90 RGB24. It reports game focus plus Raw Input/XInput activity observations. The input-health bit stays clear until physical-device coverage is validated; successful API registration alone is not enough. The D3D11 hook, exclusive-fullscreen and overlay behavior, GDI capture, window scaling, and controller coverage have not been verified in game. Python's lane and front-clear algorithms remain prototypes, and native control stays blocked until UI authorization, physical-input monitoring, the steering curve, and road perception are implemented or validated.

Build locally with `dotnet build ui/ETS2AP.Ui.slnx -c Release`. No third-party packages are required.

Run the headless checks with `dotnet run --project ui/checks/ETS2AP.Ui.Checks.csproj -c Release`. They verify English resources, theme resource loading and light/dark text contrast, preference serialization and fallback, navigation state, UI status parsing, and the fixed bundled-service launch arguments and bounded restart policy. A separate `--ipc-smoke <absolute python.exe path>` mode checks a running Python service. These checks do not validate rendered layout or game integration.
